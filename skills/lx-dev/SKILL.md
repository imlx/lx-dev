# LX-DEV — 确定性工程实施约束

`lx-dev.md` 的执行版：四阶段 **28 条硬约束**的精简形式，可独立工作。完整判据、反例与检查清单见仓库根 `lx-dev.md`（若可获得，以其为准）。

**编号与完整版一一对应**，评审可直接引用（如「违反 B2」「V7 未取证」）。

**适用范围**：任意语言、框架、代码库。与项目本地规范冲突时从严者优先。

**基本纪律**：每条结论必须附可复现证据（命令输出 / 测试计数 / SQL 结果 / 截图）。禁止「应该可以」「看起来正常」。

## 阶段一：方案（P）

**P1 标准先行**：先检索可借鉴的标准与成熟实现，给出「来源 → 做法 → 采用/裁剪/放弃理由」对照表；无先例须写明检索范围与判定依据。

**P2 两栏有据**：方案分列「必做」与「完全没必要做」，每条带依据（标准条款/实测数据/缺陷证据/需求方要求）；禁止「建议/可以考虑/视情况」；「不做」项要写清收益。

**P3 七视角自检、不限轮次**：标准一致性 / 需求与边界（反向、空数据、越权、并发）/ 可行性与工作量 / 验证可否证伪 / 降级与信息可见性 / 成本收益 / 对既有功能数据契约的影响。每轮记「视角→问题→修订」，**直到某轮零新增问题**才交付。

**P4 少分阶段、阶段内自证并自动推进**：优先单批次交付；必须分阶段时不得缩小最终范围、不得拆成需人工逐次确认的碎片；每阶段内置自动验证门，失败不限轮次自查自纠，通过即自动进入下一阶段；全程留痕，收尾一次性汇报。

**P5 冲突上报**：自证连续失败、或触及信息减少/数据不可逆时，带证据与备选方案停下上报，禁止降低判据换取推进。

## 阶段二：实施（B）

**B1 先定位后修改**：用分段计时、日志、最小复现、数据分布查询定位到具体环节，禁止凭直觉改。

**B2 禁止降级式修复**（最高优先级红线）：不得因字段装不下而截断内容、丢明细、伪造「不确定」；不得因输入过多而只处理前 N 条并标「等 N 项」；不得把「执行未完成」写成「完成」、把「保存失败」写成「判定不确定」。正确做法：结构化承载明细 + 文本列放摘要 + 单条失败显式留痕（区分保存失败与判定不确定）+ 批状态只表达执行完整性。

**B3 变更三同步**：代码模型、SQL 映射、字符串引用（查询条件/裸 SQL/脚本配置）全部同步；交付前 grep 旧名称，除历史迁移外必须 0 命中。

**B4 契约稳定**：内部改名用别名适配，不得改对外接口字段与返回结构。

**B5 迁移可验证**：结构变更必须带**逆命题**断言（断言「整改后不应再成立的状态」为 0），禁止「表已建/记录已存在」这类存在性检查；脏数据逐行处理，单行失败留原文不炸整批。

**B6 错误处理统一**：新增代码用项目统一异常体系；外部调用失败必须包装；**禁止 `return null` 静默降级**（失败要么抛出，要么返回带原因的结果对象）。

**B7 单文件单写入者**：同一文件任一时刻只能有一个编辑者；子任务报完成后，主控必须 grep 复核关键新增（分支注册、常量、路由）。

**B8 密钥不入库**：凭据、令牌、本地配置不提交；界面只回显「已配置」。

**B9 界面十条**（含 UI 时）：设计 token 唯一来源（禁裸色值、禁阶梯间游走值）/ 统一列表组件且配置驱动（禁手写分页）/ 筛选服务端全量且页码归 1，含筛选必须有重置 / 处置结果与操作人时间上列表 / 判定标签实时计算不用快照 / 主要动作一次点击可达（禁二次展开）/ 错误提示唯一出口（catch 内不重复弹）/ 状态文案中文化且缺映射显示「未知状态（原码）」/ 禁止静默覆盖或丢弃用户输入（表单须有脏值标记）/ 默认视口整页无滚动条。

## 阶段三：验证（V）

**V1 全量测试**：清理后重跑，禁止只跑增量。
- 不得以「被他人未提交改动阻塞」为由跳过——该理由必须由编译输出证实并记录。
- 失败先判归属（暂存重跑 / 比对模块交集）；自己的按最高优先级修完，他人的写明用例名+摘要+依据后放行。
- 改契约先搜测试引用（SQL 别名、记录字段、常量、方法签名、码值域）——这类改动编译期常全通过，只在断言里炸。

**V2 真实链路冒烟**：至少一条读路径（走真实 SQL/映射）+ 一条写路径 + 落库核对；只打开页面不算冒烟。

**V3 机械门禁全绿**：静态检查、类型检查、结构守卫、样式检查全绿；存量按基线只减不增，禁止用「更新基线」放行新违规。

**V4 诊断清零**：改动文件编译/静态诊断必须为 0。

**V5 覆盖如实**：N 个改动点逐点「用例+运行+确认」，禁止抽样代替全量；未验证显式标「未验证」。

**V6 独立复核**：派独立评审者看本次 `git diff`（+需求说明），禁止自我替代；Critical 立即修、Important 提交前修完、Minor 记待办；认为评审有误须给证据反驳。

**V7 交付三件套**（面向用户的功能改动，缺一即未完成）：
- 真实浏览器**断言控件真实存在**（字段序列、下拉选项、按钮文案），走完关键交互；禁止只判「页面能打开、控制台无错」；
- 涉及接口逐个实测（空数据、非法参数、越权、边界量）+ SQL 核对落库与状态流转；
- 按真实角色走通端到端业务闭环，任一步做不下去即判缺陷。

**V8 需重启即重启**：由实施者主动重启并确认端口与迁移版本，不得只回「请重启」。

**V9 验证不可互替**：单测、真实链路、浏览器/端到端各覆盖一层，必须分别执行。

## 阶段四：交付（S）

**S1 提交原子与归属**：提交前 `git status --short` 逐项确认；只加本次路径，**禁止 `git add -A`**；他人未提交改动留在工作区；误提交须在日志补「提交追溯说明」。

**S2 提交信息可回溯**：说明范围与目的，沿用 `feat|fix|docs|chore|style|refactor` 前缀。

**S3 文档同步**：影响他人理解系统的改动必须同步文档并在修订记录登记；只改代码视为未完成。

**S4 变更留痕**：日志写清真因（不是现象）、改动清单与验证证据。

**S5 四段汇报**：完成项 / 验证证据（每条结论的证据位置）/ 未覆盖未验证（显式列出）/ 未决与风险（需需求方决策）。不得把「已完成」与「未验证」混写。

## 六个不可跳过的硬门

| 门 | 判据 |
|---|---|
| 根因门 | 改动位置有证据链；无「试一下」式批改（B1） |
| 降级门 | 无截断/限流/缩范围/伪造结论；用户可见信息未减少（B2/G2） |
| 全量门 | 清理后全量测试通过，计数有记录（V1） |
| 真实链路门 | 读+写+落库核对，非仅页面加载（V2） |
| 独立复核门 | 有独立评审者针对本次 diff 的结论（V6） |
| 三件套门 | 界面断言 + 接口实测 + 业务闭环全部取证（V7） |

任一门未过，不得宣称完成。
